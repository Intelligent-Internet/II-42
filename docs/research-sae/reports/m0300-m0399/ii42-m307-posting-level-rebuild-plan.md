# M307 Posting-Level Rebuild Plan

Date: 2026-06-15

## Decision

M307 stops candidate-level residual tuning and rebuilds the training material
around true posting-level evidence.

The current M300-M306 line established useful but insufficient evidence:

- M300 aggregate evidence can safely admit tail positives.
- M302 real BM25-token/SAE-atom candidate features have top-rank signal.
- M304 atom-feature utility is the strongest atom-level smoke so far.
- M305/M306 show that generic gates and pairwise admission losses do not solve
  the problem when they are trained after candidate formation.

The next surface must let the model see how candidates are generated by
postings, not only how already-formed candidates are reranked.

## Goal

Build a new canonical material surface:

```text
query text + query embedding
-> BM25 query-token postings + SAE query-atom postings
-> posting traversal candidate generation
-> detailed matched posting evidence for selected candidates and positives
-> training rows for unified BM25-token + SAE-atom impact learning
```

This is the required bridge to a real unified sparse engine. It is not another
late fusion experiment.

## Scope

M307 prepares material, not a final model checkpoint.

The output should be suitable for multiple follow-up trainers:

- bucketed atom utility;
- posting-level admission model;
- cost-aware WAND/MaxScore simulator;
- future native payload generation.

## Required Input

For each dataset:

- `documents.jsonl` with `id`, `text`, and dense embedding.
- `documents.input.jsonl` for full text/BM25 statistics when available.
- `queries.jsonl` with `id`, `text`, and dense embedding.
- `quality_qrels.json` for supervised labels.
- PPLX1024-compatible SAE checkpoint.

The builder must reject:

- embedding dimension mismatch;
- checkpoint dimension mismatch;
- qrel positives missing from materialized document embeddings;
- empty query sets;
- empty posting-generated candidate rows.

## Two-Pass Builder

### Pass 1: Posting Traversal

For a query shard:

1. Load all selected query texts, embeddings, and qrels.
2. Encode query SAE atoms.
3. Build query token to query-id postings for BM25.
4. Build query SAE atom to query-id postings for SAE.
5. Stream the full document corpus.
6. Compute BM25 scores by traversing query-token postings.
7. Encode document SAE atoms in batches and traverse query-atom postings.
8. Maintain per-query top candidate heaps by unified posting score.

The traversal candidate score is only a material generation score:

```text
posting_score = bm25_weight * bm25_score + sae_weight * sae_score
```

It is not the final product score.

### Pass 2: Detailed Evidence Backfill

For each selected query:

1. Take top posting candidates.
2. Force include qrel positives.
3. Reload only selected documents.
4. Recompute matched BM25 token evidence.
5. Recompute matched SAE atom evidence.
6. Emit compact matched posting features per candidate.

This avoids writing the full query-document cross product while preserving the
true posting-generation path.

## Training Meaning

The future model should learn directly over posting evidence:

- which BM25 tokens are useful lexical evidence;
- which SAE atoms are useful semantic evidence;
- which high-DF atoms cause noise/fanout;
- when BM25-only, SAE-only, or overlap evidence should admit a document;
- how to keep posting cost bounded.

The model should not require existing dense ranking or post-hoc source scores
at runtime.

## Execution Plan

1. Implement `research_sae_m307_build_posting_surface.py`.
2. Validate on one small query shard with strict checks.
3. Build BEIR15 train/eval query shards dataset by dataset.
4. Collect summaries and verify exact query coverage.
5. Only after material is complete, train a posting-level utility model.

M307 material generation is allowed to use all available training nodes:

- `spark-1` and `spark-2` for GPU SAE encoding and large corpus streaming.
- `ASA` / 3090 for independent dataset shards.
- `SyxnX` and `Flora` only for CPU-heavy checking, merge, and summaries.

- M190 replay roots contain train/dev query material for several datasets.
- Therefore a builder invocation must pair qrels and query material from the

  but it intentionally rejects split mismatches.

The current reusable runner is:

```bash
scripts/run_ii42_m307_posting_surface_dataset.sh DATASET DATASET_ROOT OUTPUT_ROOT
```

It validates paths, runs the Docker-backed builder, and checks the summary for
non-empty queries, positives, and matching output row count.

After the first large-corpus attempt, the builder was tightened for scale:

- doc qrel aliases now use a BEIR materialized-id fast path instead of scanning
  the entire document JSONL before real work starts;
- qrel positive validation is performed during the BM25 statistics pass, so it
  no longer requires a separate full-corpus scan;
- selected-document token counts are cached once during detailed evidence
  backfill, avoiding repeated tokenization for every query-candidate pair.

This keeps the material semantics unchanged while removing avoidable repeated
corpus scans and repeated CPU tokenization.

## Stop Rules

Stop immediately if:

- a dataset has materialized qrel positives missing from documents;
- embedding dimensions are not PPLX1024;
- checkpoint dimensions do not match;
- positive coverage in posting candidates is worse than the existing
  candidate-union surface without a clear reason;
- runtime cost explodes before candidate quality improves.

## Promotion Gate

The material is useful only if the posting-generated candidate surface can
match or exceed the existing candidate-union baseline on positive coverage,
while reporting lower or explainable posting fanout.

The first model trained on this material must be evaluated against:

- BM25;
- SAE-only;
- existing BM25+SAE score fusion;
- M304 p50 / M304 p0 candidate-level utility.
