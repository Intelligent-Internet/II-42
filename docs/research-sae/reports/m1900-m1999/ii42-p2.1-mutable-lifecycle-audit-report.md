# II-42 P2.1 Mutable Index Lifecycle Closure

- Date: 2026-07-16
- Route: P2.1 / b1.125 real ONNX mutable lifecycle
- Model: `ii42_p2_m1934_b1125_nfcorpus_full`
- Runtime ABI: `ii42_p2_unified_text_atoms_v1`
- Final result: 25/25 lifecycle gates passed

## Executive conclusion

The three correctness failures found by the first audit are fixed on the real
P2.1 ONNX route:

1. `UPDATE` no longer leaves the prior semantic delta or immutable base row
   searchable.
2. `DELETE` now hides both immutable-base and semantic-delta documents after
   VACUUM and semantic maintenance converge.
3. Generation rotation removes semantic-delta generations derived from retired
   base generations.

Generation rebuild and publication are now one atomic operation. The rebuild
transaction holds `SHARE ROW EXCLUSIVE` on the indexed source relation before
it scans the source, switches the active generation, synchronizes identity,
and retires old state. Readers continue, while concurrent source writes wait
until publication commits.

The implementation now uses one stable logical identity across the base
generation, semantic overlay, debt ledger, tombstones, and mutable query. Heap
TIDs remain internal version locators and are tracked in a relation-owned
identity ledger as `current`, `superseded`, or `deleted`.

The mutable semantic scoring payload is now owned by the ii42 index relation.
Maintenance writes versioned EATMH002 pages under the same relation lock and
WAL lifecycle as lexical postings. Foreground query prefers that payload only
when its overlay-derived signature is current. The generation-table copy is a
temporary migration and blocking-rebuild fallback rather than the normal
scoring authority.

The original 21-gate CRUD audit passed four consecutive full executions. The
relation-owned extension passed its isolated 25-gate execution, and the generic
5,000-document lifecycle/performance smoke also passed. This closes the
previously observed CRUD correctness block and validates the new storage
boundary; it is not yet a corpus-scale throughput or long-duration concurrency
claim.

## Initial failures

The pre-fix audit passed 12/15 gates. It identified three independent defects:

| Defect | Prior behavior | Root cause |
| --- | --- | --- |
| UPDATE stale version | Old delta remained searchable | Durable semantic identity used heap TID |
| DELETE stale base row | Deleted base document remained searchable | Base used logical ID, tombstone used heap TID |
| Rotation leak | Retired semantic delta generations accumulated | Finalizer removed base state only |

An intermediate repair that read the old heap tuple during index bulk-delete
was rejected. PostgreSQL may have removed the dead heap tuple before the index
VACUUM callback runs, so `SnapshotAny` cannot provide a reliable durable ID.

## Implemented lifecycle contract

### Stable identity ledger

Model-backed mutable indexes can configure:

```sql
document_id_column = 'id',
document_identity_table = 'public.docs_body_ii42_identity'
```

`ii42_model_mutable_identity_create_table(...)` creates the ledger. Every
committed semantic insert records its logical document ID and heap TID in the
same transaction as semantic debt. A content update makes the previous TID
`superseded` and the new TID `current`.

VACUUM resolves dead TIDs through this ledger:

- `current`: emit logical-ID delete debt and mark the identity deleted;
- `superseded`: do not tombstone the newer logical document;
- aborted delta marker with no identity or overlay: reclaim without semantic
  debt;
- base tuple missing an identity: fail closed.

Generation publication synchronizes the ledger from the indexed source table.
Compaction finalization performs the same synchronization after a generation
switch, then clears retired overlay/debt state.

### Model-only DELETE visibility

P2 model-only inserts previously existed only in the SQL semantic overlay, so
the physical index had no TID for VACUUM to inspect. Each model-only insert now
writes a valid empty-value lifecycle marker into the ii42 delta segment. It
adds no lexical or P2 score and remains readable by the existing delta format,
but it gives index VACUUM an exact TID for later deletion.

Rollback is handled explicitly: the physical marker may survive an aborted
transaction, while SQL identity/debt/overlay rows roll back. VACUUM recognizes
that marker as an aborted orphan and reclaims it without creating a tombstone.
If an overlay row exists without an identity, the lookup reports corruption
instead of silently discarding semantic state.

### Base and delta replacement

Mutable queries now suppress an immutable base result whenever an active delta
has the same authoritative logical ID. Tombstones also compare the logical base
ID, with ordinal and TID fallbacks retained for older non-authoritative
generations.

### Relation-owned model delta

The model delta is stored as dedicated pages inside the ii42 index relation.
Its metapage record includes the page range, generation, record count, byte
length, and a 32-hex overlay signature. Reads validate every page header,
ordinal, generation, payload length, and EATMH magic before scoring.

Publication dual-writes during migration:

1. acquire the normal per-index maintenance lock;
2. bind the SQL overlay to one `SHARE`-locked snapshot;
3. build EATMH002 and derive the overlay signature;
4. WAL-publish model-delta pages plus the metapage switch;
5. update the compatibility generation row.

Foreground query uses `relation_model_delta` only when structure, EATMH payload,
and overlay signature all match. Otherwise it fails safely to the validated
generation row. Online ii42 maintenance preserves the relation payload. A
blocking `REINDEX` creates a fresh relation, so the validated fallback remains
queryable until ordinary semantic maintenance republishes the same payload into
the new relation.

Publication is serialized with the same `ShareUpdateExclusiveLock` used by
ii42 maintenance. Payload and metapage writes use full-page WAL, while relation
payload loads hold `ShareLock`. If a transaction aborts or PostgreSQL crashes
between page publication and SQL fallback publication, page generation and
overlay-signature validation make the incomplete relation copy ineligible;
foreground query therefore continues from the last validated generation.

### Generation retirement

`ii42_model_mutable_compaction_finalize(...)` now deletes every semantic-delta
generation whose `base_generation_id` differs from the active generation. The
final test state contains only `p2_mutable_v4`; no v1-v3 base or semantic-delta
generation remains.

The finalizer resolves the indexed source relation and acquires
`SHARE ROW EXCLUSIVE` before identity synchronization or retired-state cleanup.
The public runtime text-table builder acquires the same source lock before its
first scan, so direct API users receive the same consistency contract.
The tested rotation helper acquires the same lock before building the staging
generation and keeps the staging build, generation switch, finalization, and
old-generation deletion in one transaction. This closes the write window in
which a generation could previously be published from a stale source snapshot.

## Final audit sequence

The release gate creates an isolated PostgreSQL 18 cluster and uses the actual
P2.1 ONNX checkout. It performs:

1. base generation build with authoritative logical IDs;
2. transaction containing INSERT, UPDATE, and DELETE followed by rollback;
3. committed insert, maintenance, relation publication, and byte parity against
   the compatibility generation;
4. online maintenance with relation payload and result preservation;
5. blocking `REINDEX`, generation fallback, and relation republish;
6. immediate PostgreSQL crash and recovery with relation payload preservation;
7. two consecutive updates before VACUUM and maintenance;
8. update of an immutable-base document;
9. delete of an immutable-base document;
10. insert, delete, and reinsert of the same logical ID;
11. model-only insert/delete with both lexical rebuild thresholds disabled;
12. full rebuild and generation rotation;
13. 24 concurrent reads while committed writes are maintained;
14. repeated generation rebuilds and deterministic digest comparison;
15. clean restart and final ledger/storage invariants.

Run it with:

```bash
python3 scripts/test_p2_mutable_lifecycle_smoke.py \
    --output \
    runs/ii42-p2.1-mutable-lifecycle-audit-v2/p2_mutable_lifecycle_audit.json
```

The command fails by default if any gate is false.

## Remaining boundaries

- `document_id_column` is a stable product identity. Change it with DELETE plus
  INSERT rather than an in-place ID mutation.
- Eventual DELETE convergence requires VACUUM (normally autovacuum) followed by
  semantic maintenance. This audit executes both explicitly.
- Generation rotation currently blocks source INSERT, UPDATE, and DELETE for
  the duration of the rebuild transaction. SELECT remains available. An online
  tail-catch-up protocol is future work; correctness does not depend on it.
- The concurrency check is short and correctness-oriented. A long-running,
  corpus-scale mixed mutation soak remains a separate performance/reliability
  gate.
- The immutable base semantic generation still uses generation-table/cache
  storage. This change converges mutable scoring ownership first; it does not
  yet claim that all semantic bytes share the physical ii42 relation.
- The current query helper validates and copies the relation EATMH payload into
  a backend bytea before evaluation. A direct page-backed evaluator is the next
  latency and allocation optimization.
- The generation row remains a required blocking-`REINDEX` fallback during the
  migration. It can be retired only after rebuild can carry or republish the
  relation payload atomically without that safety copy.
- The identity ledger adds one durable row per live or uncompacted historical
  heap version. Generation compaction removes historical states and restores
  one current row per source document.

## Decision

Promote stable logical identity, model-only TID lifecycle markers,
relation-owned model-delta pages, and retired semantic-delta cleanup as the
P2.1 mutable CRUD baseline. The product lifecycle is now BM25-shaped: ordinary
index mutation, WAL, maintenance, rebuild, and VACUUM semantics, with the
encoder queue as the only model-specific asynchronous stage. The next work is
direct relation-page scoring and corpus-scale mixed-mutation performance, not a
second semantic sidecar lifecycle or another CRUD identity redesign.
