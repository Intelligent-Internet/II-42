# II-42 P2.1 Unified Index Product Health Audit

- Date: 2026-07-17
- Extension version: `0.1.2`
- Product route: one lexical and semantic posting index
- Model: `ii42_p2_m1934_b1125_nfcorpus_full`
- Runtime ABI: `ii42_p2_unified_text_atoms_v1`

## Executive Conclusion

P2.1 now uses one PostgreSQL index lifecycle. A semantic-enabled index is
created with `sae = true`; the same `ii42_query`, status, maintenance, and
drop APIs apply to both index modes.

Lexical pages, semantic pages, the ordinal-to-TID map, and mutable state are
owned by one physical index relation. Each complete build writes private
replacement sections and publishes them through one metapage manifest switch.
A query cannot combine sections from different publication ids. If semantic
encoding or validation fails before that switch, the previous complete
generation remains visible.

The release gate passed:

- fresh PostgreSQL 18 catalog creation;
- the standard PGXS integration regression suite;
- 21/21 unified lifecycle gates;
- 20,000-document native lifecycle validation;
- five-run same-machine BM25 regression comparison;
- native semantic-enabled query and concurrency smoke.

No corpus-generation table, semantic overlay, semantic debt ledger, model
registry, or document-identity sidecar is part of the product route.

## Product Shape

```text
CREATE INDEX ... USING ii42 ... WITH (sae = false/true)
    -> one heap scan
       -> lexical tokenizer -> lexical posting pages
       -> optional encoder  -> semantic posting pages
       -> shared document ordinal and physical TID map
    -> validate every required section
    -> one metapage manifest publish
    -> ii42_query(...)
```

The two posting sections remain contiguous so their scorers can read them
efficiently. This physical locality does not create two indexes or two
lifecycles: only the shared manifest makes either section visible.

## API Contract

| Operation | API |
| --- | --- |
| Build | `CREATE INDEX ... USING ii42 ... WITH (sae = false/true)` |
| Search | `ii42_query(...)` |
| Inspect | `ii42_index_options(...)`, `ii42_index_status(...)` |
| Maintain | `ii42_index_refresh/maintain/try_maintain/maintain_due` |
| Drop | `DROP INDEX` |

`sae = true` is only a build capability switch. It does not select another
application API. A fresh `0.1.2` catalog does not install the retired
`ii42_model_*`, `ii42_sae_*`, or `ii42_index_model_*` product families.

`ii42_index_status(...)` reports one generation object with lexical,
optional semantic, and delta sections. The semantic object is a section
descriptor; it deliberately has no independent generation id.

## Lifecycle Verification

The isolated lifecycle smoke passed 21/21 gates:

| Surface | Result |
| --- | --- |
| Initial build | Lexical and semantic sections share one atomic manifest |
| Public API | Product role uses only `ii42_query(...)` |
| Catalog shape | No split lifecycle functions or sidecar relations |
| INSERT | One new complete generation becomes query-visible |
| UPDATE | One new complete generation replaces the old document version |
| DELETE | Committed deletion is immediately filtered |
| VACUUM | Dead rows are removed and both sections converge together |
| REINDEX | Ranking digest is preserved |
| Failed rebuild | Complete previous generation remains active |
| Eventual writes | One pending state; one maintenance operation converges both sections |
| BM25-only mode | Same manifest format with semantic section absent |
| Restart | Both index modes remain ready and preserve results |
| Drop | PostgreSQL removes the whole index without sidecar cleanup |
| Mixed soak | Ten CRUD/VACUUM cycles and 100 repeated queries converge |

The failed-rebuild gate deliberately points the index at a missing checkout,
runs `REINDEX`, and verifies that generation identity and ranking remain
unchanged. This tests the exact lexical-written/semantic-failed boundary that
would otherwise expose a partial index.

## Medium Native Validation

The 20,000-document semantic-enabled route exercises:

- complete initial build;
- first and warm query;
- batch mutation;
- unified maintenance;
- post-mutation query;
- `REINDEX`;
- status validation and drop.

The active manifest contains 20,000 lexical documents and exactly 20,000
semantic records. The semantic section starts after the lexical pages and both
sections carry the same generation number. Timings on this scalar-path Mac are
operability evidence, not production capacity estimates.

| Operation | Result |
| --- | ---: |
| Initial table and unified index build | 41,292.47 ms |
| First query | 34.40 ms |
| Warm query | 33.41 ms |
| Batch CRUD | 25.06 ms |
| Unified maintenance | 41,336.78 ms |
| Post-mutation query | 35.36 ms |
| REINDEX | 41,185.29 ms |
| Drop | 27.00 ms |

The first publication used generation 1 with 398 lexical pages followed by 70
semantic pages. Maintenance published generation 2 with the same section
counts and a new shared boundary. The test exited successfully without leaving
its temporary PostgreSQL cluster running.

## BM25 Regression Gate

The BM25-only route was compared against the pre-convergence baseline on the
same Mac, PostgreSQL version, NFCorpus payload, and query set. Each side used
five isolated runs over 3,633 documents and 3,237 queries.

| Metric | Baseline median | Unified-code median | Delta |
| --- | ---: | ---: | ---: |
| Query throughput | 3,145.68 QPS | 3,167.26 QPS | +0.69% |
| Query p50 | 0.2824 ms | 0.2768 ms | -1.96% |
| Query p95 | 0.5092 ms | 0.5075 ms | -0.32% |
| Index build | 102.55 ms | 102.89 ms | +0.33% |

The small build difference is within observed run-to-run variance. Query
throughput and latency do not regress, so the disabled semantic branch does
not impose a measurable BM25 hot-path penalty on this surface.

## Semantic-Enabled Performance

The real P2 checkout, 1,000-document product smoke measured:

| Metric | Result |
| --- | ---: |
| Unified index build | 9.93 s |
| Physical index size | 1,376,256 bytes |
| Warm query mean range | 6.51-7.39 ms |
| Concurrent readers | 4/4 successful |

This includes text encoding and native posting traversal through
`ii42_query(...)`. It is substantially below the historical 109-163 ms SQL
vector-plus-BM25 fusion examples, but those older numbers used a different
corpus and execution shape. They are directional evidence, not a controlled
same-corpus A/B claim.

## Storage And Failure Invariants

1. One `ii42_am_generation_manifest` names every active physical section.
2. Lexical and semantic pages are written before metapage publication.
3. Both sections use the same generation number and document ordinal space.
4. Semantic record count must equal the lexical document count.
5. `sae = true` rejects lexical-only staged publication and lightweight fold.
6. One metapage write publishes or rolls back the complete replacement.
7. A replacement reserves its next generation before any relation truncation,
   so generation identity stays monotonic within the index lifecycle.
8. WAL, crash recovery, replication, backup, `REINDEX`, and `DROP INDEX`
   apply to the containing relation rather than to sidecar objects.

## Remaining Limits

1. The current failure test covers a deterministic encoder failure before the
   manifest switch. A longer fault-injection soak should also kill PostgreSQL
   during lexical write, semantic write, WAL flush, and immediately after the
   switch.
2. The 20,000-document route is a medium gate. Large-corpus SLOs still require
   per-corpus build, bytes, posting visits, p50/p95/p99, and memory limits.
3. Runtime checkout files remain external executable configuration. They are
   not corpus state, but deployment must version them with the extension and
   restart policy.
4. Historical research generation-table functions remain research primitives,
   not product lifecycle APIs. They should move to a separate research package
   if the extension catalog itself must contain only product surfaces.

## Release Judgment

The lifecycle convergence is valid and should be retained. P2.1 is now one
physical inverted index with optional semantic pages, one publication
boundary, and one application lifecycle. The next product work is extended
fault and large-corpus SLO validation, not another sidecar compatibility
layer.
